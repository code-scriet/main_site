## F11 — eiows never loaded on the contest relay (High, perf)

> **Fixed.** Now loaded via `createRequire(import.meta.url)`, matching `apps/api/src/utils/socket.ts`. Confirmed at runtime: the boot log went from the fallback error to `[relay] Socket.IO using eiows (C++) WebSocket engine (low-memory default)` — eiows was installed and building fine all along.

**Found while verifying F2** (it surfaced in the playground boot log), not in the static pass.

**Where:** [apps/playground/execute-server.js](../../apps/playground/execute-server.js) — `resolveRelayWsEngine()`

```js
const { Server } = require('eiows');   // ← ReferenceError: require is not defined
```

`apps/playground/package.json` sets `"type": "module"`, so this file is ESM, where a bare `require`
does not exist. The call threw `ReferenceError` on **every** boot, was caught by the surrounding
fallback handler, and silently pinned the relay to stock `ws`. The main API does it correctly with
`createRequire(import.meta.url)`; only the playground had the bare call.

**Impact.** CLAUDE.md documents eiows as the DEFAULT on "api + playground" and as "the lever that
raises the ~900-concurrent ceiling" (≈5-8× lower per-connection memory). The playground relay is
the box that holds **every contest WebSocket** (200-250 students) — precisely the workload eiows
was adopted for — and it had never once run it. The failure was "loud" as designed, but the log
line blamed a failed native build, so the real cause (an ESM/CJS mistake that can never succeed)
read as an environment problem.

Second-order: `WS_ENGINE_STRICT=true`, documented as the way to make a regressed native build fail
the deploy, would have **unconditionally refused to boot the playground**, since the load could
never succeed regardless of whether eiows was built.

## F1 — Unauthenticated 12 MB body parse on public `/internal/*` (High)

> **Fixed.** The secret check is now app-level middleware ahead of the 12 MB parser, plus a 120/min/IP limiter. Verified at runtime: an unauthenticated 2 MB body returns **403 in 25 ms unparsed**; a correctly-signed call still returns `{"ok":true}`. `getJwtSecret`/`deriveInternalSecret` moved above the middleware chain (with a comment pinning the ordering, since a TDZ there would be swallowed by `deriveInternalSecret`'s own catch and silently disable the relay).

**Where:** [apps/playground/execute-server.js:86](../../apps/playground/execute-server.js#L86)

```js
app.use('/internal', express.json({ limit: '12mb' }));   // ← parses BEFORE any auth
app.use(express.json({ limit: '1mb' }));
...
app.post('/internal/plagiarism', async (req, res) => {
  if (!validInternalSecret(req)) return res.status(403).json({ error: 'forbidden' });
```

The secret check lives **inside the handler**, so `express.json` has already buffered and
`JSON.parse`d the full body by the time the request is rejected. `/internal/*` also carries **no
rate limiter** — `crudRateLimit` is attached per-route to the authenticated `/api/*` handlers only,
and there is no app-level limiter on this service.

`codescriet-playground-api` is a public Render web service (`render.yaml`), so this is reachable
from the open internet. CORS is not a defense: the origin callback explicitly allows origin-less
requests (`if (!origin) return callback(null, true)`), and CORS never blocks a non-browser client
anyway.

**Impact.** An unauthenticated attacker POSTs 12 MB bodies in a loop. Each one costs a 12 MB
allocation plus a **synchronous** `JSON.parse` that blocks the event loop. This box is a free-tier
512 MB instance that now hosts the contest `/competition` Socket.io relay — stalling its event loop
drops every contestant's socket mid-round, and the plagiarism offload with it. Trivial to trigger,
no credentials, no account.

**Fix.** Move the secret check ahead of the parser and bound the route:

```js
const internalLimiter = rateLimit({ windowMs: 60_000, max: 120, keyGenerator: (req) => req.ip });
app.use('/internal', internalLimiter, (req, res, next) =>
  validInternalSecret(req) ? next() : res.status(403).json({ error: 'forbidden' }));
app.use('/internal', express.json({ limit: '12mb' }));
```

`validInternalSecret` only reads a header, so it is safe to run pre-parse. Keep the in-handler
checks as defense in depth. Consider dropping the limit to what a real batch needs — the preferred
`{ roundId, problemIds }` path sends a handful of ids, and the 12 MB ceiling only exists for the
legacy `items` path.

## F2 — Playground auth ignores `tokenVersion` and `isDeleted` (High)

> **Fixed.** `optionalAuth` now checks both gates through a 30s bounded cache using `pool.query` directly (not `dbQuery`, which swallows errors into `[]` and would make a DB blip look like "user not found"). Fails **open** on DB fault — this runs on every request and the prior behavior was no check at all. `/internal/disconnect-user` invalidates the cache so a kick lands on the next request. The `/competition` socket `join` also compares `token_version`. Two hazards closed while making `optionalAuth` async: `extractToken` could throw `URIError` on a malformed cookie, and an async rejection under `app.use` would **hang** the request rather than 500 — the body is now fully wrapped so `next()` always runs. Verified: valid token authenticates, malformed cookie → prompt 401 (no hang), purpose-carrying token → 401.

**Where:** [apps/playground/execute-server.js:145-175](../../apps/playground/execute-server.js#L145)
(`optionalAuth` / `requireAuth`), and
[apps/playground/execute-server.js:1939](../../apps/playground/execute-server.js#L1939) (`authSocket`).

The main API's `authMiddleware` enforces two DB-side gates on every request
([apps/api/src/middleware/auth.ts:135-143](../../apps/api/src/middleware/auth.ts#L135)):

```ts
if (user.isDeleted === true) return res.status(401)...
if (user.tokenVersion > claimVersion) return res.status(401)...   // force-logout
```

The playground does **neither**. `optionalAuth` verifies the JWT signature and rejects
purpose-carrying tokens, then trusts the claims wholesale — no user row is ever read.

**Impact.** `POST /api/users/:id/force-logout` bumps `tokenVersion`, invalidates the auth cache,
and calls `disconnectUserSockets` — but the target's existing 7-day JWT keeps working against the
playground indefinitely. Dropping their sockets is cosmetic: they reconnect with the same token.
A force-logged-out user retains `/api/execute` (code execution against the shared daily quota),
snippets, session, history and prefs. During a contest, force-logout is the lever a PRESIDENT uses
to remove a cheater — and it does not remove them from the arena's execution path.

Soft-delete is partially mitigated: `DELETE /api/users/:id` upserts auto-blocks, and `/api/execute`
does check `isUserBlocked`, so a deleted user can't execute. But snippets/prefs/session/history
stay open to them, and **force-logout alone creates no block**, so that path has no mitigation at all.

The contest socket is in better shape — `join` re-reads `role` + `is_deleted` from the live DB
([execute-server.js:1975-1982](../../apps/playground/execute-server.js#L1975)) — but it still does
not compare `tokenVersion`, so a force-logged-out (not deleted) user can rejoin the round.

**Fix.** Add a short-TTL user-row lookup mirroring `userAuthCache.ts` (30 s bounded LRU keeps this
near-free — the playground already has `pool`):

```js
// after jwt.verify, before setting req.user
const { rows } = await pool.query(
  'SELECT token_version, is_deleted FROM users WHERE id = $1', [decoded.userId || decoded.id]);
if (!rows.length || rows[0].is_deleted) return null;
if ((rows[0].token_version ?? 0) > (decoded.tokenVersion ?? 0)) return null;
```

Cache it 30 s so the per-request cost stays a map hit. Add the same `token_version` comparison to
`authSocket`'s `join` handler, which already pays for one user lookup there.

## F3 — `mark-read` accepts an unbounded future cutoff (Medium)

> **Fixed.** Extracted as the pure `resolveReadCutoff(at, now)` and clamped to now (unparseable input also falls back to now rather than writing an Invalid Date). Covered by 6 new tests in `notificationsReadCutoff.test.ts`.

**Where:** [apps/api/src/routes/notifications.ts:257-270](../../apps/api/src/routes/notifications.ts#L257)

```ts
const markReadSchema = z.object({ at: z.string().datetime().optional() });
...
const cutoff = parsed.data.at ? new Date(parsed.data.at) : new Date();
await prisma.user.update({ where: { id: auth.id }, data: { notificationsReadAt: cutoff } });
```

`z.string().datetime()` validates *shape*, not range. Any value is accepted — including
`2099-01-01T00:00:00Z`.

The whole bell is built on this single cutoff: every item computes `read: timestamp < readCutoff`.
A future cutoff marks **all present and future notifications read, permanently**, across
invitations, certificates, quiz starts, system events and admin broadcasts. There is no UI to
reset it — `mark-read` only ever writes forward from the client's perspective.

This is not purely theoretical. The current web client sends no `at`, but a device with a skewed
system clock is the classic trigger, and any future client that passes `new Date().toISOString()`
from client time inherits the bug.

**Fix.** Clamp server-side, and reject the nonsense case rather than silently accepting it:

```ts
const now = new Date();
const requested = parsed.data.at ? new Date(parsed.data.at) : now;
const cutoff = requested > now ? now : requested;
```

Consider a one-off repair for any user whose stored `notificationsReadAt` is already in the future.

## F4 — Proctor instant-violation budget never resets on unlock (Medium)

> **Fixed.** The instant tally is now scoped to violations after the participant's last `unlockedAt`, so an admin **Unlock** restores the warning. The append-only log is untouched — only the lock decision resets. Query is served by the existing `[roundId, userId]` index.

**Where:** [apps/api/src/routes/competition.ts:2778-2784](../../apps/api/src/routes/competition.ts#L2778)

```ts
const instantCount = await tx.competitionViolation.count({
  where: { roundId: round.id, userId: user.id, kind: { in: [...INSTANT_VIOLATION_KINDS] } },
});
lock = instantCount > INSTANT_VIOLATION_BUDGET;   // budget = 1
```

The count is **cumulative for the whole round** and `CompetitionViolation` is an append-only log —
nothing clears or watermarks it. `POST /proctor/unlock/:userId` sets `locked = false` but leaves the
tally untouched.

**Impact.** Once a contestant has tripped two instant violations, the admin's **Unlock** is
effectively a no-op: the very next `COPY_PASTE` or `FULLSCREEN_EXIT` re-locks them instantly, with
no warning, because `instantCount` is permanently past the budget. Instant kinds include *copy* and
*cut*, not just paste — a reflexive Ctrl+C, or one browser-driven fullscreen drop, is enough. With
200-250 students, an invigilator who unlocks a student is going to be unlocking them repeatedly for
the rest of the round.

This looks like unintended behavior rather than policy: the code deliberately builds a
warn-then-lock budget, and the unlock endpoint exists to hand a student a second chance. The second
chance currently isn't one.

**Fix.** Record the unlock instant and count only violations after it. `CompetitionParticipantState`
already carries `unlockedAt`:

```ts
const state = await tx.competitionParticipantState.findUnique({
  where: { roundId_userId: { roundId: round.id, userId: user.id } }, select: { unlockedAt: true },
});
const instantCount = await tx.competitionViolation.count({
  where: { roundId: round.id, userId: user.id, kind: { in: [...INSTANT_VIOLATION_KINDS] },
           ...(state?.unlockedAt ? { at: { gt: state.unlockedAt } } : {}) },
});
```

The full log is preserved for the monitor and for post-hoc review; only the *lock decision* resets.

## F5 — ~20 `useMemo`s that never memoize (Medium, perf)

> **Fixed.** All 12 offending declarations (covering the ~20 downstream memos) now derive through `useMemo` keyed on the query data, so identity is stable across renders. The 2 remaining `exhaustive-deps` cases were deliberate narrow dep lists — documented and suppressed at the dependency-array line so they stop masking real signal. `exhaustive-deps` is now **0**.

`npm run lint --workspace=apps/web` reports **91 warnings, 0 errors**:

| Rule | Count |
|---|---|
| `react-hooks/set-state-in-effect` | 57 |
| `react-hooks/exhaustive-deps` | 20 |
| `react-hooks/purity` | 7 |
| `react-hooks/refs` | 4 |
| other | 3 |

The `exhaustive-deps` cluster is one repeated mistake, not twenty separate ones:

```tsx
const all = query.data || [];                 // new array identity every render
const filtered = useMemo(() => all.filter(...), [all]);   // ⇒ recomputes every render
```

Worst offenders: `EventCertificateWizard.tsx` (10), `AdminScanner.tsx` (6),
`ProfilePage.tsx` / `DashboardOverview.tsx` / `CompetitionMonitor.tsx` / `UserDetailContent.tsx` (4 each).

`CompetitionMonitor` is the one that actually matters — it is the live contest console, patched in
place by socket events at contest cadence, and it re-derives its participant tables on every one of
those renders.

**Fix.** Hoist the default inside the memo (`useMemo(() => (query.data ?? []).filter(...), [query.data])`)
or memoize the default itself. Mechanical, low-risk, and it clears the warning class.

The 57 `set-state-in-effect` warnings are mostly the legitimate
"fetch-then-setState in an effect" shape and are lower priority, but they are worth a pass to
distinguish real cascading-render bugs from noise — right now the signal is buried.

## F7 — Public certificate verify writes on every read (Low, perf)

> **Fixed.** New `utils/certificateViewCounter.ts` buffers increments and flushes every 30s as one `UPDATE … FROM (VALUES …)`. Bounded at 500 certIds with early flush on overflow, single-flight, re-buffers on failure, and drained by the shutdown path so a redeploy loses nothing.

**Where:** [apps/api/src/routes/certificates.ts:1262-1266](../../apps/api/src/routes/certificates.ts#L1262)

```ts
prisma.certificate.update({ where: { certId: cert.certId }, data: { viewCount: { increment: 1 } } })
  .catch(() => {});
```

`GET /api/certificates/verify/:code` is unauthenticated and public. Every hit — including crawlers,
link-preview bots and scanners — issues a DB **write**. Bounded only by the anonymous IP limiter at
2000/15 min, i.e. ~2.2 writes/sec/IP sustained, against a Neon pooled link where connection
round-trips are the scarce resource (the stated reason the round/registration caches exist).

Also note this is the one `.catch(() => {})` left in the API that logs nothing.

**Fix.** Buffer increments in a bounded in-memory map and flush periodically with a single
`updateMany`-style batch (the retention-prune tick is a natural home), or drop `viewCount` to
best-effort sampling. Either way, log the failure rather than swallowing it.

## F8 — `roundCache` size cap is advisory, not enforced (Low)

> **Fixed.** Oldest-first eviction now runs after the expired-sweep, so the cap holds even when nothing has expired. Two new tests pin it via a `debugRoundCacheSize()` seam.

**Where:** [apps/api/src/competition/roundCache.ts:149-151](../../apps/api/src/competition/roundCache.ts#L149)

```ts
if (roundCache.size >= roundMaxEntries) {
  for (const [k, v] of roundCache) if (at - v.at >= roundTtlMs) roundCache.delete(k);
}
```

The sweep only removes **expired** entries. If more than 64 distinct rounds are polled inside one
10 s window, nothing is expired, nothing is evicted, and the map grows past its documented bound.
Real-world round counts make this harmless today, but the file's header states the cache is
"bounded 64" under HC #1, and it isn't. Add an oldest-first eviction fallback after the sweep so
the invariant is actually enforced rather than asserted.

  changes how everyone's toolchain resolves and belongs in its own decision.

# Review round 2 — defects found in the fix commit

Two independent code reviews of the F1-F11 fixes. Grouped by whether the fix commit caused them.

## Regressions introduced by the fixes (now corrected)

**The F1 rate limiter was itself a DoS lever, and throttled real traffic.** `app.use('/internal',
internalLimiter, gate)` metered requests *before* the secret check, and this service sets no
`trust proxy`, so `req.ip` is Render's edge-proxy address for every caller — the main API's
server-to-server emits and an attacker's junk shared ONE 120/min bucket. Two consequences, both
silent: (a) legitimate traffic exceeds 120/min on its own, since the leaderboard broadcast is
throttled to 1/sec per ACTIVE round and issues TWO POSTs (roomAll + roomAdmin), before any
submission/violation/proctor/clarification events; (b) anyone could spend ~2 req/s to exhaust the
bucket and starve every relay push. `relayEmit` is `void fetch(...).catch()`, and a 429 *resolves*
the fetch, so nothing was caught, logged, or fell back — the arena and admin monitor would just go
stale while their sockets stayed connected, which also means the REST-polling fallback (keyed on
`connected`) never engages. **Fixed:** a valid secret is trusted and bypasses the limiter entirely;
only rejected callers are metered (60/min/IP). `relayEmit` now logs non-2xx. Verified: 200
consecutive authenticated emits all return 200, unauthenticated is bounded at 429, and
authenticated still succeeds *after* an attacker exhausts their bucket.

**`flushCertificateViews` short-circuited instead of chaining.** `if (flushInFlight) return
flushInFlight` returned the in-flight promise without draining what had accumulated since its
snapshot, breaking both of the module's guarantees: a SIGTERM landing mid-flush awaited the OLD
batch and dropped every view recorded since (despite the "a redeploy loses nothing" claim), and the
`MAX_PENDING_ENTRIES` overflow trigger was a no-op for the duration of a slow query, letting the
buffer grow past its documented bound. **Fixed:** chained (`flushInFlight.then(() => flush())`),
which terminates naturally once `pending` is empty. Also latched a `stopped` flag so a late
`/verify` request cannot re-arm the interval behind the shutdown drain.

**`requireAuth` re-ran `optionalAuth`.** `app.use(optionalAuth)` already resolves `req.user` before
any route, so the route-level guard repeated the whole extractToken → jwt.verify →
`isAccountRevoked` sequence — cheap when that was a signature check, but the F2 fix turned it into
a path that can hit the DB. It was also unsound: `optionalAuth` only ever *assigns* `req.user` and
never clears it, so a first pass failing open on a DB blip left a `req.user` a stricter second pass
could not retract. **Fixed:** `requireAuth` is now a plain `req.user` check.

## Pre-existing defects also fixed

- **`isAccountRevoked` had no single-flight and did not cache the missing-user case.** The arena
  polls several endpoints per contestant in parallel and every contestant's TTL is seeded at contest
  start, so each 30s boundary produced ~4 simultaneous identical queries per user against the
  playground's hardcoded `max:5` pool. Separately, `rows.length === 0` returned before the cache
  write, so a token for a hard-deleted account re-queried on *every* request for the rest of its
  7-day life. Both fixed; mirrors `roundCache.ts`, which caches the in-flight promise for the same
  reason.
- **`shouldReloadForStaleChunk` wedged permanently on a future timestamp.** `now - lastReloadAt >=
  COOLDOWN` stays negative forever if the stored instant is ahead of now (clock corrected backwards,
  NTP jump — routine on student laptops), disabling stale-chunk recovery for the whole session.
  Fixed in both copies, mirroring the clamp applied to the notification cutoff.
- **`setAutoReloadBlocked` was a boolean, not a ref count** — the same overlapping-owner problem
  that `MobileSheet`'s scroll lock ref-counts. With two `useProctor` consumers (or a StrictMode
  double-mount) the first cleanup cleared the block while another instance was still live, re-arming
  the self-inflicted reload that burns a contestant's only FULLSCREEN_EXIT warning.
- **`downloadCode` revoked the blob URL synchronously**, cancelling the download on Safari/Firefox
  while still firing the success toast. Now revoked on the next tick.
- **`usePlaygroundActions` returned a bare object literal**, so `PlaygroundPage`'s `mobileActions`
  useMemo recomputed every render and re-rendered `MobileActionBar` through `React.memo` — strictly
  more work than no memo. Now memoized.
- **`useMediaQuery`'s `getSnapshot` built a new `MediaQueryList` per call**, and React calls it on
  every render plus again after each render to check tearing — several media-query parses per second
  on the phones this module exists for. Now one cached `MediaQueryList` per query.
- **The mobile Output pane was conditionally rendered**, so each Code↔Output flip remounted
  `OutputPanel`, fired a fresh authenticated `getSessionBootstrap()` and discarded tab/history/stats
  and any typed interactive input. Now hidden-not-unmounted, matching the code pane two lines above.
- **`CommandPalette` used `onMouseDown` for tap-outside-to-dismiss** — the exact pattern
  `MobileSheet` rejects, since touch browsers suppress the synthetic mousedown once a touch sequence
  is preventDefault'd. Now `onPointerDown`.
- **`audit-gate.mjs` matched exceptions on GHSA id alone.** A reviewed exception kept suppressing an
  advisory even after it attached to a package the written justification never covered — e.g. the
  react-router RSC entry is justified by "no `@react-router/server|node|dev` present", so adding one
  would have sailed a reachable CSRF bypass through a green gate. Exceptions are now package-scoped
  and name the uncovered package when they fail.
- **`ProblemPanel` and its context slice were unreachable dead code.** `setCurrentProblem` — the only
  writer that sets `showProblemPanel: true` — has *never* had a caller (verified across history), so
  the panel could never render. Removed the component, the render branch and the four dead context
  fields. This was not a regressed feature; it never worked.

## Test rigor

- **The F8 eviction test was vacuous.** With `roundMaxEntries: 3` and exactly 3 rounds, the
  `size >= max` check (evaluated *before* insert) never saw 3, so the eviction branch never ran and
  the assertion passed for the wrong reason — deleting the entire eviction block would have kept it
  green. Rewritten to use `max + 1` rounds and to assert **behaviourally** (an evicted round
  re-queries), which also catches wrong-order eviction. Mutation-checked: both tests fail when the
  eviction loop is removed and pass when restored.
- **`debugRoundCacheSize()` was removed** from the `RoundCache` interface — a test-only seam should
  not widen a hot-path production contract when the property is assertable through the public API.
- **`resolveReadCutoff` moved to `utils/notificationCutoff.ts`.** Importing it from the router made
  the DB-free stability suite evaluate the whole router module and construct the Prisma client. This
  mirrors the existing `certificateIssuance.ts` extraction: the route file is the HTTP adapter.

## Knowingly not taken

- **`chunkReload.ts` duplication across web/playground.** Real, and the two
  `shouldReloadForStaleChunk` signatures have already forked (`blocked` exists only in the
  playground copy). Deduping needs a shared workspace package that this monorepo does not have, so
  it is a build-config change rather than a code fix. Both copies were fixed in lockstep here.
- **The `useMemo(() => x ?? [], [x])` idiom** could be a module-level `EMPTY` constant with no hook
  at all. Correct, but re-churning eleven just-reviewed files for a stylistic win is worse than
  leaving a working pattern in place. Worth doing as its own cleanup.
